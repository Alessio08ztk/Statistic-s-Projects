Terms I had to keep apart

Key generationCreating fresh secret randomness (the entropy behind the mnemonic). Only this step needs a good random source.
Key derivationDeterministically computing keys from something that already exists (seed → child keys). Same input, same output, always.
Public-key cryptosecp256k1: a pair (private k, public Q = kG) with a one-way link; used for signatures.
HashingKeccak-256: fixed-size fingerprint, no key, one-way, avalanche behaviour.
ChecksumEIP-55: extra redundancy to detect typos; not secret and not a security measure against attackers.
EncodingJust a representation of bytes (hex, word lists, letter case). Reversible, no secrecy at all.

Historical context


    

  • 1977 – RSA. First practical public-key system.
    • 

  • 2001 – SHA-2 / SHA-512. Standardised by NIST; BIP-39 later uses it inside HMAC/PBKDF2.
    • 

  • 2012 – BIP-32. Hierarchical deterministic wallets: one seed, a tree of keys.
    • 

  • 2013 – BIP-39. Mnemonic words that encode the seed.
    • 

  • 2014 – BIP-44. Standard paths for multi-account, multi-coin wallets (m/44'/60'/0'/0/0 for Ethereum).
    • 

  • 2015 – SHA-3. NIST standardises Keccak (the winner of a 2012 competition). Ethereum was already using the pre-standard Keccak.
    • 

  • 2016 – EIP-55. Mixed-case checksum for addresses.
    • 



SHA-2 vs Keccak/SHA-3. SHA-2 is a Merkle–Damgård design (compression function chained over blocks); SHA-3 is a sponge built on the Keccak-f[1600] permutation, so it is a completely different internal structure chosen partly as a "plan B" if SHA-2 ever broke. Ethereum's Keccak-256 predates the final standard: NIST changed the padding/domain-separation bytes, so Keccak-256 ≠ SHA3-256 even though the core is identical (the demo above shows it).



Why so many different techniques?


Each step solves a different problem and needs different properties:


    

  • BIP-39/32/44 – key management: back up 12–24 words instead of many keys, derive an unlimited, reproducible tree of keys in a standard layout so wallets are interchangeable.
    • 

  • secp256k1 – a one-way relation between private and public key that also allows signatures others can verify without learning the secret. A hash alone can't do that.
    • 

  • Keccak-256 – compresses a 64-byte public key into a 20-byte identifier and hides the raw public key until the first transaction.
    • 

  • EIP-55 – catches typos at essentially no cost, without changing the address format.
    • 



Statistical angle: the seed, private key and Keccak output should all look uniformly random; the Keccak step should show avalanche; EIP-55 is deliberately pseudo-random as well, so a single wrong letter breaks the pattern with probability about 1 − 2⁻ᴸ (L = number of letters, ~15 on average → ≈ 99.99%).

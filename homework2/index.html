Homework 2: Wallet Seed → Ethereum Address

Seven small steps, seven different jobs. Open each step, then play with the labs further down.

The pipeline, step by step

1. Entropy random bits → nothing yet

key generation Everything starts with 128–256 bits from the system's secure random generator. This is the only moment a wallet really generates a secret. Every later step is deterministic.

2. BIP-39 entropy → words → 512-bit seed

encodingderivation A short checksum is appended to the entropy and the bits are cut into 11-bit pieces, each one an index into a 2048-word list (12 words for 128 bits). Then PBKDF2-HMAC-SHA512 (2048 rounds, salt "mnemonic" + optional passphrase) turns the sentence into a 64-byte seed. The words are an encoding, the seed is a derivation.

3. BIP-32 seed → tree of keys

derivation HMAC-SHA512 with the key "Bitcoin seed" gives a master private key and a chain code. Each child is another HMAC of (parent key, chain code, index). From one seed you can recompute an endless tree, and a hardened index (≥ 2³¹) stops anyone from walking up the tree using public data.

4. BIP-44 convention for the tree

convention No new cryptography here, only an agreement on the path layout m/44'/coin'/account'/change/index, so a wallet from one vendor finds the same keys as one from another. Try the builder below.

5. secp256k1 private k → public (x, y)

public-key crypto Q = k·G on y² = x³ + 7 over a 256-bit prime field (the toy version of this is Homework 1). The 64-byte public key is what signature verification needs; the private key never leaves the wallet.

6. Keccak-256 public key → 20-byte address

hashing Hash the 64 raw bytes of x‖y (without the 0x04 prefix) and keep the last 20 bytes. It compresses the key and hides it until the first signed transaction.

7. EIP-55 address → checksummed address

checksumencoding Hash the lowercase hex address; every letter whose matching hash nibble is ≥ 8 is written in capitals. The address itself is unchanged, the casing is the checksum.

    Where this sits in time
    

      

    • 1977 – RSA, the first practical public-key scheme
      • 

    • 2001 – SHA-2 / SHA-512 standardised (used inside BIP-39 and BIP-32)
      • 

    • 2012 – BIP-32, hierarchical deterministic wallets
      • 

    • 2013 – BIP-39, mnemonic sentences
      • 

    • 2014 – BIP-44, multi-account path standard
      • 

    • 2015 – SHA-3 standardised by NIST, based on Keccak
      • 

    • 2016 – EIP-55, mixed-case address checksum
      •

    Ethereum adopted Keccak before NIST finished the standard. NIST then changed the domain-separation bytes, which is why the two functions give different digests for the same input (Lab 2 shows it).
    


    Why not one algorithm for everything?
    

    

    PieceProblem it solvesWithout it
    

    BIP-39 / 32 / 44one backup, reproducible keys, standard layouta file of random keys per account, wallets incompatible
    

    secp256k1signatures that anyone can verify without the secretnobody could prove they own an address
    

    Keccak-256short, fixed-size, one-way identifier64-byte public keys everywhere, exposed early
    

    EIP-55typo detectionone wrong character sends funds to nowhere
    

    

    Statistical side. Entropy, seed, private key and hash outputs should all look uniform. Only the hash is expected to show avalanche (Lab 2). The EIP-55 pattern is pseudo-random too, so a single typo survives only with probability about 2⁻ᴸ, where L is the number of letters in the address (about 15 on average). Lab 3 puts a number on that.
